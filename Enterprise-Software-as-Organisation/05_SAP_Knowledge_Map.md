# SAP Knowledge Map

This map defines empirical targets; it is not evidence that any construct appears in every scoped process. Each observation must be registered with product, release, retrieval date, and source status.

| Construct family | Technical meaning | Organisational significance | Candidate interpretation | Evidence to collect | Overinterpretation risk |
|---|---|---|---|---|---|
| Enterprise structure | Configured entities and relationships such as company, company code, plant, storage location, purchasing organisation, sales organisation, and controlling structures | Partitions responsibility, transactions, reporting, and access; connects differentiated domains | Encoded structural differentiation and jurisdiction | Entity definitions, allowed relationships, assignment cardinalities, creation/change constraints, process use | Treating a legal/accounting object as a complete social unit; assuming configured values |
| Reference process | Vendor-provided solution process with steps, actors, objects, and flows | Proposes a division and ordering of work | Process-level coordination configuration | Process flow, test script, task descriptions, prerequisites, variants, exceptions | Reading a happy path as actual or exhaustive practice |
| Business role | Template or configured aggregation connecting job-function concepts to catalogues/apps and restrictions | Defines a possible bundle of responsibilities and access | Encoded division of labour or decision domain | Role-template definition, catalogues, apps, restrictions, process-step actor | Assuming role template equals job or assigned authority |
| Authorisation | Permission model using roles, catalogues, apps, restrictions, and users | Delimits legitimate action and information visibility | Access right; structural jurisdiction; potential separation of duties | CRUD/action rights, restriction types and values, assignment model, explicit SoD guidance | Equating app access with decision rights or accountability |
| Workflow | Scenario, start/step conditions, agent determination, tasks, deadlines, exception handling | Routes obligations, sequences decisions, allocates approval | Planning, direct supervision, rule-based coordination, escalation | Fixed versus configurable portions, condition logic, recipients, outcomes, deadline effects | Assuming workflow is active or followed; collapsing all routing into supervision |
| Business rule | Condition, decision table, validation, determination, or derivation | Encodes a decision premise or standard | Standardisation, formal control, bounded discretion | Inputs, operator, output, owner, scope, edit authority, fallback | Calling technical calculation governance without an organisational consequence |
| Master data | Relatively persistent shared objects used by transactions | Stabilises categories and provides common references | Pooled coordination; information integration; classification | Object definition, ownership, reuse, validation, change governance, organisational scope | Assuming consistency, meaning, or universal visibility from a shared model |
| Status/document flow | State representation and links among business documents | Compresses history, gates later action, enables traceability | Exception signal, sequential coordination, accountability trace | State definitions, transition conditions, allowed actions, downstream effects | Treating display-only labels as mechanisms |
| Configuration | Supported setting of scope, structure, parameters, and process options | Allocates sanctioned design choices | Bounded organisational discretion | Configuration activity, allowed values, role, lifecycle, transport/change constraints | Conflating configuration possibility with customer choice |
| Extensibility | Released mechanisms for fields, logic, forms, integrations, or side-by-side extensions | Defines where deviation can be represented inside the supported architecture | Bounded deviation and architectural governance | Extension point, eligible objects, lifecycle, upgrade guarantees, restrictions | Treating technical extensibility as unlimited organisational flexibility |
| Fiori app | Task-oriented user application associated with catalogues and roles | Presents an action and information environment to a role | Interface-level enactment of division, visibility, and control | App ID, purpose, role/catalogue, input/output, related process step | Inferring the whole process from an app description |
| SAP Signavio Process Navigator | Repository for solution processes, roles, capabilities, and reference business architecture | Exposes the vendor's explicit representation of work | Primary map of encoded process logic | Release/package, diagrams, accelerators, linked setup/test content | Treating model completeness or marketing taxonomy as executable truth |
| SAP Best Practices | Preconfigured scope and implementation content, including solution processes and test scripts | Articulates a normative starting arrangement | Reference template for fit and standardisation | Scope-item/solution-process ID, version, roles, prerequisites, steps, configuration links | Treating “best” as empirically superior |
| Fit-to-Standard | SAP Activate activity comparing scoped standard processes with customer requirements and recording gaps/backlog | Makes acceptance, configuration, extension, and redesign choices discussable | Sensitising concept: organisational-design negotiation | Official method, workshop inputs/outputs, decision categories; later, observed workshop records | Claiming negotiation dynamics or outcomes from method documents alone |

## Process-domain collection map

For P2P collect requisition-to-payment dependencies, supplier/master-data relations, sourcing and purchasing roles, approvals, goods/service receipt, invoice matching, blocks, release, and accounting integration. For O2C collect customer and sales-area structures, order creation, availability/credit controls where in scope, fulfilment, billing, receivables, document flow, and exceptions. For R2R collect journal-entry creation/approval, organisational ledgers and company-code scope, period-end activities, validations, allocations, consolidation interfaces where scoped, and reporting visibility.

Boundary decisions must be written before collection. “P2P”, “O2C”, and “R2R” are analytical umbrellas, not SAP artefact identifiers. Each included solution process must have its own official identifier and release. Cross-domain events are duplicated only by reference: one source record, multiple coded relations.

## Source topology

SAP Signavio Process Navigator supplies process and role representations; SAP Help Portal supplies product behaviour and configuration constraints; the Fiori Apps Reference Library supplies app–role–catalogue relations; SAP Best Practices setup/test content supplies procedural detail; SAP Learning may clarify method. SAP Community is secondary commentary and receives a lower evidence grade. Marketing pages can establish vendor positioning only, not architectural behaviour.
