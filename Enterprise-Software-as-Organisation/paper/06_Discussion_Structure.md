# Discussion Structure  -  Conditional Pathways

## Enterprise software as codified organisation design

Evidence needed: systematic representation and operationalisation of differentiation, dependency, information, rights, and control across domains. Novelty lies in specifying an analytical object and method, not in saying software affects organisation. Drop or narrow if observations remain a disconnected feature inventory.

## Software organisational primitives

Evidence needed: recurring constructs whose operations can be coded reliably and whose relational configurations explain mechanisms. This may extend coordination theory by locating mechanisms in software constructs. Drop the term if primitives lack stable inclusion criteria or add no explanatory value over “feature”.

## Configuration as bounded organisational discretion

Evidence needed: documented allocation of sanctioned design choices plus fixed boundaries and organisational consequences. This could connect enterprise-system configuration to decision-right theory. Drop if empirical variation is only technical parameterisation.

## Fit-to-Standard as design negotiation

Paper 1 can establish only the encoded template and official method logic. A full contribution requires workshop/interview and decision data. Keep as future proposition unless architectural evidence shows which organisational dimensions the method explicitly exposes. Drop from Paper 1 if it distracts from supported findings.

## Boundary contribution

Whatever positive claims survive, the discussion should show why encoded, implemented, and enacted levels must remain distinct. Explain where Thompson, Mintzberg, and Galbraith illuminate the architecture, where categories overlap, and where machine-enforced mechanisms require refinement. Avoid claiming that classical theory is “operationalised” unless evidence shows more than an analyst's retrospective classification.
